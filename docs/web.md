# Web — Documentación técnica

## Capítulo 1 — Rutas, configuración, usuarios y modelos

**Alcance:** la aplicación Django que envuelve al motor. Cubre configuración,
usuarios/roles, modelos, vistas, API, plantillas y JavaScript de la web reducida.

**Stack:** Django 6.1, PostgreSQL 16 + pgvector 0.6, Django REST Framework,
Tailwind por CDN, sesiones y autenticación por rol.

**Web reducida (2026-10-22):** solo tres secciones visibles:

| Ruta | Pantalla |
|---|---|
| `/directorio/` | Registro con video y listado de registrados |
| `/sesiones/` | Historial de capturas y detalle |
| `/en-vivo/` | Control de asistencia en vivo |

El resto de páginas académicas (panel del profesor, reportes, auditoría, mapa de
salones) sigue existiendo por URL, pero fuera del menú.

## 4. `apps/users/permissions.py` (47 líneas)

### `role_required()` (líneas 6-26)

```python
def role_required(*roles):
    """
    decorador para vistas basadas en funciones que restringe el acceso
    a usuarios que tengan uno de los roles especificados.
    """
    def decorator(view_func):
        @wraps(view_func)
        def _wrapped_view(request, *args, **kwargs):
            if not request.user.is_authenticated:
                return redirect('login')

            # los desarrolladores siempre tienen acceso completo
            if request.user.is_superuser or request.user.role in roles:
                try:
                    return view_func(request, *args, **kwargs)
                except PermissionDenied:
                    return redirect('dashboard')

            return redirect('dashboard')
        return _wrapped_view
    return decorator
```

- **Línea 6:** recibe los roles permitidos como argumentos.
- **Línea 12:** `@wraps` conserva el nombre y docstring de la vista.
- **Línea 14-15:** sin sesión → login.
- **Línea 18:** superusuario **siempre** pasa, aunque su rol no esté en la lista.
- **Línea 19-20:** si el rol está permitido, ejecuta la vista.
- **Línea 21-22:** si la vista lanza `PermissionDenied`, redirige al dashboard.
- **Línea 24:** rol no permitido → dashboard.

### `RoleRequiredMixin` (líneas 29-47)

```python
class RoleRequiredMixin(AccessMixin):
    """
    mixin para vistas basadas en clases que restringe el acceso
    a usuarios que tengan uno de los roles especificados.
    """
    allowed_roles = []

    def dispatch(self, request, *args, **kwargs):
        if not request.user.is_authenticated:
            return self.handle_no_permission()

        # los desarrolladores tienen acceso completo
        if request.user.is_superuser or request.user.role in self.allowed_roles:
            try:
                return super().dispatch(request, *args, **kwargs)
            except PermissionDenied:
                return redirect('dashboard')

        return redirect('dashboard')
```

- **Línea 34:** cada vista declara `allowed_roles`.
- **Línea 36:** `dispatch` es el primer método que se ejecuta en una vista basada
  en clases.
- **Línea 37-38:** sin sesión, `handle_no_permission` (login).
- **Línea 41-45:** mismo criterio que el decorador.
- **Línea 47:** rol no permitido → dashboard.

**Uso típico:**

```python
@role_required("PROFESSOR", "COORDINATOR", "DIRECTOR")
def live_attendance(request):
    ...

class PanelProfesorView(RoleRequiredMixin, ListView):
    allowed_roles = ["PROFESSOR"]
```

```python
    @property
    def posible_fuga(self):
        if not self.hora_entrada or not self.ultima_vez_visto:
            return False
        today = datetime.today()
        dt_entrada = datetime.combine(today, self.hora_entrada)
        dt_visto = datetime.combine(today, self.ultima_vez_visto)
        diff_seconds = abs((dt_visto - dt_entrada).total_seconds())
        return diff_seconds < 900
```

  profesor lo revisa.

## 15. Flujos completos

### 15.1 Registro desde `/directorio/`

```
Usuario → modal → carnet + nombre + video (archivo o cámara)
   → FormData → POST /api/enrolar/ (CSRF)
       → RegistroBiometricoView:
           valida → guarda temp → enrolar_usuario_headless
               → 15 muestras → centroide → _guardar_db (no crea usuario)
           → crea User(username=carnet) + FaceEmbedding
           → borra temp
       → 201 {exito, estudiante}
   → JS agrega la fila y cierra el modal
```

### 15.2 Asistencia en `/en-vivo/`

```
Usuario → elige sesión y fuente → Iniciar
   → POST /api/en-vivo/iniciar/
       → servicio_en_vivo.iniciar → hilo _bucle
           → VideoCapture → motor → aplicar_decisiones
           → escribe RegistroAsistencia
           → guarda JPEG
   → JS consulta /api/en-vivo/estado/ cada 1 s
   → JS pinta /api/en-vivo/frame/ cada 300 ms
   → Detener → POST /api/en-vivo/detener/
```

### 15.3 Revisión de una sesión

```
/sesiones/ → tabla con contadores
   → /sesiones/<id>/ → filas + capturas
       → Descartar (POST) → alerta_revisada=True
```

## 16. Seguridad

| Aspecto | Estado |
|---|---|
| Login | Obligatorio para `/directorio/`, `/sesiones/`, `/en-vivo/` |
| Roles | `role_required` / `RoleRequiredMixin`; superusuario pasa |
| Estudiantes | No pueden iniciar sesión (`AdministrativeModelBackend`) |
| CSRF | Tokens en formularios y cabecera `X-CSRFToken` |
| Cookies | `HttpOnly`, `SameSite=Lax`, expiran al cerrar |
| Video temporal | Se borra en `finally` |
| Validación de carnet | Regex `^[a-zA-Z0-9_-]+$` |
| Duplicados | `409` si el username ya existe |
| `/api/enrolar/` | `IsAuthenticated` + rol `DEVELOPER`/`COORDINATOR`/`DIRECTOR` |
| Credenciales | `CV_DB_*`, `DJANGO_SECRET_KEY`, `DJANGO_DEBUG`, `DJANGO_ALLOWED_HOSTS` |

**Pendiente para producción:**

- **`media/` se sirve por Django** solo en `DEBUG`; en producción debe hacerlo el
  servidor web.
- **Endurecer el entorno:** `DJANGO_DEBUG=0`, `DJANGO_ALLOWED_HOSTS` con el
  dominio real y `DJANGO_SECRET_KEY` propia.
- **Rate limiting** en `/api/enrolar/` (hoy solo hay autenticación y rol).
